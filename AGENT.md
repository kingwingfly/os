## Architecture and invariants

- The rules (owner's design, 2026-10-29): the kernel holds no command logic, and runs no commands: programs are user space's (crates/userland, the page). Every check is the kernel's, call by call; user space is untrusted, and only asks. Errors are errno, with coreutils' wording in the programs (`rm: cannot remove 'x': Permission denied`). New behaviour is a system call with its errno, or a program over the calls; never an endpoint. The API is `/api/sys`, the byte I/O (`/api/file`, `/api/pwrite`) and the events socket, nothing else.
- System calls (owner's design, 2026-10-29: the page is user space, the API its system calls; see README, Architecture): `crates/abi` is the interface, the calls (`Call`), their batch (`Batch`: the process's umask and sudo) and results, and errno with glibc's words; `crates/kernel` is the file system's syscalls, one function each, every check Linux's (namei, generic_permission with ACLs, sticky, protected links, ACLs as `system.posix_acl_*` xattrs), over the `Fs` store, tested on `MemStore`; `crates/worker/src/sys.rs` serves `POST /api/sys`, each call its own transaction. A call changes one name or inode, or fails and changes nothing; walking a tree is user space's. New file-system behaviour belongs in the kernel, as a syscall with its errno, never in a command the server runs.
- File descriptors (`crates/worker/src/fds.rs`, the `fds` table): `open`, `pread`, `pwrite`, `close` and `ioctl(FICLONE)` are system calls; a call may name an earlier call's descriptor (`{"ref": i}`, `sys::resolve`), and `pread`/`pwrite` carry up to 256 KiB as base64 in the batch, moved to or from R2 outside a transaction (`sys::bytes`); larger chunks stream on the Worker (`PUT /api/pwrite?fd=&index=`, files.rs), as `GET /api/file` reads them. Every batch keeps its session's descriptors (`fds::renew`, at most every 5 s per session, `sys::heard`); pages holding one say so every 8 s (web/http.mjs `hold`). A writer that gives no size writes in order: the file grows (`File::growing`), truncated as it opens, whole when it closes or when its writer is gone. Directories open to read (`O_DIRECTORY`); /proc is `procfs.rs`, and `/proc/self/fd/N` is a magic link followed in every call's paths (`sys::paths`). A descriptor is its session's (`auth::sid`: a signed-in session's key, or the browser's own `os_guest` cookie, which the Worker gives a browser at once, `lib.rs with_guest_cookie`). Uploads (web/upload.mjs), the editor's save, recordings (web/record.mjs, `O_APPEND`), `cp` (FICLONE) and the seed script write through them; nothing writes a file otherwise, but archive jobs, until processes (phase 5). A descriptor call stands as it ends, failed or not (sys.rs): a close that fails still closes. Numbers are each given once per session (`fd_numbers`, forgotten with the session, or once it is idle with none open): pages share a session's descriptors, so a reused number could name another page's file. A descriptor opened as root (the call's cred, under sudo too) is marked `root`, and every check on it later, the Worker's streams included (`fds::acting`: pwrite, written, close, by_token), is root's. FICLONE shares /usr's binaries (`usr:*` content ids, read from the Worker's assets: `fds::Read::Asset`, `sys::asset_range`), and refuses what the kernel makes as it is read with EOPNOTSUPP, which userland cp copies by reading (`Copy::write_read`). The WASI engine sends its deferred closes after a batch's calls, so `{"ref": i}` names the caller's i-th.
- User space (`crates/userland`): the programs, as coreutils are (ls, stat, df, mkdir, rmdir, rm, mv, cp, ln, readlink, realpath, touch, chmod, chown, chgrp, getfacl, setfacl, getfattr, setfattr, fd, ps, kill), each an async function over `Sys` and nothing else; dates as GNU's (`time.rs`, UTC); ps and the shell's jobs read /proc (`procs.rs`); GNU's messages (`rm: cannot remove 'x': Permission denied`), silent on success but with -v; trees walked a level a batch (`walk::below`), never atomically. The page runs them (`Shell::program`, over `crates/frontend/src/sys.rs`); unit tests run them over the kernel in memory (`userland/src/tests.rs`). Names come from /etc/passwd and /etc/group, which the kernel generates as they are read (`sys::generated`). E2E tests reach the kernel through `tests/sys.js` (`sys`, `errno`, `mkdirp`, `rmrf`, `listing`, `entry`, `put`, a whole file written through a descriptor, and `program`, a small user space of the setup programs; `fakeKernel` for pages without a server).
- Core: pure Rust path resolution, the shell grammar (pipelines, xargs items, fd placeholders: `shell.rs`), text filters (`text.rs`), fd matching (`find.rs`), fuzzy completion, ranges, and the `Store` trait (`permissions.rs`: names, inodes, accounts, and the helpers that still walk paths for jobs and the account commands: `physical`, `traverse`, `access`, `writable_parent`, `mkdir`, `remove` (userdel -r's home), `move_home`). `MemStore` implements it for tests; the worker's `Db` over SQLite. The file system's calls and their rules are the kernel's (`crates/kernel`, one function a call, tested on `MemStore`); the old command methods (`rename`, `link`, `symlink`, `chmod`, `chown`, `walk`) were removed as duplicates of them (2026-11-04). New file behaviour is a kernel call.
- Frontend: Leptos tabs (`lib.rs`); each tab is a `shell::Shell` that runs pipelines stage by stage, and the programs of user space (`Shell::program`, `sudo_program`), whose questions (`mv -i`, `cp -i`) go to the tab's next line; xargs and fd -x run each command on its own, so each asks. web/app.js's `accountCommand` keeps the dialogs and hands the rest back to run as programs. Text filters, xargs and fd -x/-X run in the page. Browser bridge in web/app.js; chunked uploads in web/upload.mjs. CodeMirror loads lazily.
- Previews render in Rust: crates/frontend/src/viewer.rs mounts each into the viewer's content through `window.osPreview.show(content, path, kind, version)`, and app.js calls what it returns to release it; the mount happens only if `content.dataset.version` still names that open. app.js keeps the dialog shell, fullscreen, games, and focus handling. Markdown is sanitized with ammonia; maths is substituted after sanitizing.
- The viewer's search (`crates/frontend/src/search.rs`, the `Searchable` wrapper of text, code, diff and Markdown previews) matches Rust regular expressions over the DOM's text nodes and highlights them with the CSS Custom Highlight API, never changing the preview's markup; it searches again when the markup changes (code highlighting arrives later). It shows `#viewer-search` in the viewer bar while mounted, and its Esc must not close the viewer.
- crates/preview builds seven web workers (scripts/build.mjs): PDF (hayro), archive listings (zip, tar, flate2, with an expanded-byte budget; the main bundle has no archive code), diagram (merman, size profile), and four code groups (arborium). A loader whose wasm fails to load answers `[0, false, error]`, the failure of call 0 (ready); the page then stops that worker, so the next call starts a fresh one. Grammars are C: building needs clang with wasm32 and llvm-ar. Each worker file must stay under Cloudflare's 25 MiB asset limit; split a language group if one grows past it. The upload allowlist (core `kind`) must cover every previewable extension; a frontend test checks the highlighted languages.
- The AUTHORITY Durable Object named filesystem keeps all metadata in SQLite tables (`crates/worker/src/db.rs`). Every request's decisions and writes run in one `db::transact`, a hand-bound `transactionSync`: **never await inside it**. Do async work (reading the body, password hashing, rate limits) before, and re-check in the transaction what it relied on. A reply of 400 or more rolls back unless it is marked `keep()` (cleanups).
- **File bytes never pass through the authority.** The Worker (`files.rs`) asks it to authorize (`/internal/read`, `/internal/upload/begin|chunk`), streams R2 natively (no copying through wasm, `FixedLengthStream` for known lengths), then asks it to commit, which checks again. Downloads therefore never wait on uploads.
- Files have a fixed chunk size (8 MiB for chunked uploads; a single-request PUT is one chunk), so chunk i starts at i × chunk_size; the readable length of an uploading file is its contiguous committed prefix. A new file's node exists while it uploads; an overwrite swaps at completion only if the node still shows the file it replaces. Every chunk authorization, chunk commit and completion checks the destination again (`api::destination`): a new file where its node is now (it may have moved), while the uploader can traverse to it and owns it or may write it; an overwrite while the uploader may write the target that still shows its base.
- Storage: `nodes(path → ino)` are names, `inodes` hold owner, group, mode (with setuid/setgid/sticky), file id, link target and ACLs (JSON, core `acl`), `xattrs(ino, name, hex)`. `Store::set_node` with `ino` 0 makes an inode, otherwise updates that inode and names it; an inode goes with its last name. `Node.links` is computed (directories: 2 + subdirectories). The schema version is `meta.schema` (db::SCHEMA_VERSION); older local state is refused with a message to delete it, as nothing is migrated.
- Paths given to the Store rules are physical up to their last part: callers resolve with `Store::physical(who, path, follow)` (`commands::command_path` follows a final link, `entry_path` does not; API endpoints use `real!`). Physical resolution stops, leaving the rest as written, where the caller may not search or nothing is, so the rule that follows reports the usual error. protected_symlinks is enforced there and in the kernel's namei; protected_hardlinks in `kernel::link`; the sticky rule in the kernel's `unlinkable` (unlink, rmdir, rename, and what replaces a name).
- New nodes come from `permissions::created` (umask 022 or the parent's default ACL, setgid group inheritance); do not build `Node::file(who…, 0o644…)` for user-made files.
- Nodes refer to immutable file ids; copies share them. A store frees a file when no node refers to it, by putting its key prefix `chunks/<file>/` in `garbage` in the same transaction; the alarm lists and deletes everything under it (also objects written but never committed) and expires uploads idle for 24 hours. Home moves, mv and cp change metadata only.
- Every chunk write has its own R2 key (`chunks/<file>/<index>-<random>`, from `api::chunk_key`), and a chunk is committed once: a write sent again, late, or after completion is discarded, never overwriting bytes a reader, copy or completed file uses.
- The initialization marker (`system/os-authority-v2`) fails closed if the authority's storage disappears.
- Archive jobs are processes (owner's design, 2026-10-29; `jobs.rs`, `runner.rs`): `spawn {argv, cwd}` (zip, unzip, tar, faststart; ENOENT for anything else) starts one as the caller (root under sudo), owned by the account signed in, and gives a descriptor of its standard input (`/proc/PID/fd/0`), which unzip's answers are `pwrite`n to (`jobs::answer`); /proc/PID lists the account's (procfs.rs); `kill` signals one (its owner's or root's: EPERM, ESRCH), `wait {pid, since}` gives its state and what it wrote after `since` (waitid with WNOHANG, and a read of its output). sys.rs wakes the runner after spawn, an answer and kill. The shell follows a process it spawned (`Shell::follow`); `ps` and `kill` are user space's programs (userland `procs.rs`). `spawn` validates and snapshots the inputs in one transaction, pins the files they read (`job_files`, which garbage collection respects), then wakes a `JobRunner` (one per job, named by its id). The runner works from its alarm in bounded steps, keeps its plan in its own SQLite, and acts as the job's process (Phase 4, below): its file calls are the system calls, with the job's token. Its container (`crates/jobs`) only reads and writes archives on its disk; bytes between R2 and it are streamed, never copied through wasm.
- Accounts are system calls (owner's design, 2026-10-29; sys.rs): `login`, `logout`, `sudo`, `passwd`, a signed-out `useradd` with a password, and an account's own `userdel` with its password run the kernel's handlers of them (api.rs `login`, `sudo`, `passwd`, `register`, `unregister`: rate limits, the KDF outside a transaction, the session cookie set on the batch's reply); root's `useradd`, `usermod`, `userdel`, `groupadd`, `groupmod`, `groupdel` are `commands::accounts`, given their options parsed by user space (crates/userland `accounts.rs`, as are whoami, id, groups and users, of /etc/passwd and /etc/group). web/app.js keeps the dialogs (su, login, logout, passwd, sudo -u/-k, a guest's useradd, an account's userdel of itself) and hands anything else back to the shell to run as a program (`{program: true}`). The server runs no commands; `/api/command`, `/api/login` and the rest are gone. Tests reach the account calls through `tests/sys.js` `api(request, name, {headers, data})`, answered with the statuses the endpoints had.
- Guests: `guest` is a real, locked account (uid/gid 65534, home `/guest`, `root:guest` 1777). A signed-out `useradd [-m|-M] [--short-password] NAME` (app.js's dialog; other options need sudo) makes an account with a private group, membership in guest, home `/guest/NAME` (made 700 with -m only, as useradd), and signs in; it is rate-limited ("register") and capped (`REGISTERED_MAX`). An account in group guest deletes itself (`userdel` with its password, app.js's dialog, for `userdel [-r] NAME` signed in as NAME), its password checked, by `commands::accounts::delete_account`, which root's userdel runs too: -r removes a home only if it is the account's own directory, and its same-name group goes unless another account is in it. A home not made yet is its account's alone to make (`Store::writable_parent`, `home_of`), as /guest is anyone's to write in. `protect_home` ignores guest's home for homes inside it.
- Commands (owner's request, 2026-10-27) are defined once, for clap, in core `cli/` (one module per manual section): a `#[derive(Parser)]` struct whose doc comment is the summary and description and whose fields' docs are the options, plus `impl Manual` for the section, needs, examples and see-also; each is listed in `cli::DEFINITIONS`. Parse arguments with `cli::parse::<T>`, never by hand: its errors are clap's, on one line ("NAME: reason; NAME -h shows how to use it"). `-h`/`--help`, `help` and `man` pages are generated from the definitions (`cli::help`, `cli::page`, `cli::index`; man gets its pages through `window.osManual`); `-h` is help unless the command defines a short `-h` of its own and has more arguments, or runs with `-h` alone (`df -h`) (`cli::wants_help`). Running a command is a program of user space (crates/userland `run`, over the system calls) or a `TerminalCommand` in frontend `shell/commands.rs` (what needs the page: open, upload, stream, present, cd, filters); a defined command with neither is sent to app.js's `accountCommand`, for its dialogs. A new command is a definition and a program (or a terminal entry); what the kernel must decide is a system call.
- `faststart FILE` is an archive job (`Job::Faststart`): the runner's `create` sends the file as input 0 and calls the container's `POST /faststart` (`crates/jobs` `faststart.rs`, a qt-faststart-style relocation) instead of `/build`, then writes the result over the file in place (`replace`). A 422 from the container ends the job with one error line, not retries; `already` ends it without writing. The upload warning for non-faststart MP4s points to it.
- Archive output must stay deterministic (pinned mtime, owners from the snapshot, miniz_oxide at a fixed level, fixed gzip header bytes): a resumed `zip`/`tar -c` rebuilds and compares chunk SHA-256s with what is stored, and starts the upload over on any difference. A change to the job container that changes bytes is fine only because of that check; keep it.
- Extraction follows Linux: members written in place one by one, unsafe ones (`..`, devices, duplicates) skipped with a warning (core `archive::member_path`), a cancelled or interrupted member's upload cancelled so no partial file remains. unzip's replace question is asked once, for all conflicts, before writing (`state = question`). Links in archives: members `symlink`/`hardlink` (`crates/jobs` `Kind`), planned with their target in `plan.link`; symbolic links are made in a second pass after all other rows. Replacing a file during extraction unlinks it first (`runner::open_write` with `unlink`), then makes it anew (`O_CREAT|O_EXCL`, its archive mode set by `chmod` past the umask); `tar -c` over an existing archive still writes the inode in place (`O_TRUNC`). A link that replaces a file is made beside it and renamed over it. What the job looks at (`lstat`) or writes is checked as any process's call is: traversal before a node is told of. The runner's KV key `planned` says planning finished, so an empty plan ends the job rather than plan again; error counts carry over from planning and earlier steps via the job's progress. Modes (`runner::extracted_mode`): unzip the archived bits, tar those less 022, or for root all of them, 000 included (`Member.mode` is `None` when a zip has none: 644/755); a file gets its mode as it is made; directories, at the end, whenever their current mode (`lstat`) differs, those that were there before too. `jobs::view` pages 500 lines with `more`; the shell drains every page before treating a job as ended. Guests' jobs act as guest.
- Owner/group/other select exactly one class, without bit union or fallback. Root uid 0 retains complete control. Check all ancestor x bits before inspecting protected contents.
- Authorize HEAD, Range, and conditional requests before returning data or 304. Keep private/no-store, Vary Cookie, nosniff, and file-response sandbox/CSP behavior; SVG is served as `image/svg+xml` only because of that sandbox and its `Content-Disposition: attachment`.
- File creation needs parent w+x; overwriting needs file w; deletion needs parent w+x. Recursive operations validate the entire affected tree before mutation.
- Some HTTP error classification currently matches English message fragments. Preserve 401/403/404/409 semantics when editing messages; permission/API tests cover these paths. A future typed-error refactor must preserve behavior.

## Phase 1 findings (2026-11-01)

The kernel split and the first process model are in place; these are built features, not
roadmap.

- **Client kernel:** `crates/client-kernel` is Rust→wasm, built `--target no-modules` and
  imported by `web/kernel/client.js`, a classic SharedWorker. It holds the browser's process
  token table and asks `/api/sys` through the `self.kernelSys` transport that page script
  installs. `web/kernel/protocol.js` is the page's versioned envelope (`v: 1`, one reply per
  request id); `web/app.js` starts it at `started()`, and `web/wasi/exec.mjs` asks it for every
  coreutils process. Two tabs of one browser share the namespace and see each other's pids.
- **Process registry (moved 2026-11-03, change request 1):** each browser's namespace is a
  `Machine` Durable Object of its own (`MACHINE`, `id_from_name(ns)`, `machine.rs`), whose
  SQLite has `namespaces`, `account_boots`, `processes`, `cgroups`, `spare` (lent pids) and `revoked` (tokens
  the authority is still to revoke); `procs.rs` is its registry. A namespace is the browser's
  guest key (`session.<key>` with no guest cookie). `ProcInit` creates PID 1 (root's, as
  Linux's; signals to it do nothing) and the root cgroups; a new boot id reaps only the
  current account's old processes. Rules:
  - **Routing:** `Call::is_registry` names the registry's calls (a Kill or Wait of a number
    too). The client kernel marks its batches `X-Registry: 1`, and the Worker sends them to the
    machine by the cookies' namespace; the machine refuses any other call (ENOSYS). A page's
    batch to the authority that carries registry calls has them forwarded (`machine::forward`,
    `/internal/sys`) with the caller the authority found.
  - **execve asks the authority for credentials and an image:** the machine gives each stage
    a pid (`exec_begin`), asks the authority once for the whole pipeline (`/internal/exec`, with the browser's cookies), and
    records each row (`exec_end`). Tokenless registry bookkeeping also resolves the account
    once per batch through `/internal/identity`. The authority (`creds.rs`) checks with
    `kernel::executable`
    (regular, whole, X rule, root's x rule, no setuid), snapshots uid/gid/groups/umask into
    `credentials` by the token's hash, and answers an asset for a build binary (by content) or,
    for an uploaded image, a process-owned descriptor and read token.
  - **Credentials, not rows, at the authority:** a process's file calls and byte requests are
    checked by `Db::credential` in the caller's namespace. A fork carries its parent's token (it
    keeps its credentials and shares its descriptors). Descriptors are owned by the credentials'
    `owner`: the exec's `"ns pid token-prefix"`, or, for an image a process replaced its own with,
    the one it had (`credentials.owner`, a line of images with the same credentials), so an exec
    keeps what the process opened; an image's own descriptor is owned by its token alone
    (`Credential::image`). The machine revokes a token once no live process holds it (`revoked`),
    at the end of the batch that ended it (`/internal/revoke`, which closes its image's
    descriptor, and its line's once no credentials of the line are left), the alarm retrying; a
    replaced image's token is revoked by the exec itself.
  - **A process's own execve:** `Execve` with `pid` and the process's own token (`proc`, checked
    by `exec_begin`), which only the client kernel's `reexec` sends for its host: the image is
    replaced, the pid, cgroup and credentials kept (the authority snapshots the old token's, not
    the caller's), and the process carries a new token. Without the token, a pid cannot be
    taken over (EPERM).
  - **Local fork, exit and wait:** the client kernel forks with a lent pid (`Pids`, at most
    `PIDS_MAX`, within `PROC_MAX`), keeps exits and waits in its own table, and tells the machine
    in order (`Fork`/`Exit` naming the process by `pid` and `proc`), with its next request or
    25 ms after (`client.js` `report`); its requests go one at a time (`serially`). `wait`
    returns after the machine heard, so `/proc` agrees. An exit reparents children to init;
    zombie orphans are reaped at once.
  - **Signals:** a machine `Kill` is told to the hosting tab through the authority's events
    line (`/internal/tell`, `Told::Namespace`). `Gone { seat }` ends a gone tab's processes as
    SIGKILL; `Seats` lists the seats still running.
  - **/proc** lists the machine's processes (`machine::list`), fetched before the transaction;
    a pread through a descriptor that turns out to be /proc's asks again with them
    (`fds::Read::Processes`). Init is listed for everyone.
- **Batch identity:** `abi::Batch` gains `pid` and `proc`. A process's batch runs as the
  credentials snapshotted at exec, never as the page signed in later; it cannot login, logout,
  sudo or change the session. Page batches omit both and keep the old meaning.
- **Guest identity:** signed-out browsers are `guest-<uuid>:guest`, uuid the first 16 hex digits
  of the cookie key's SHA-256, uid from 1,000,000–1,999,999 (`guests` table, `users` lookup
  falls back to it), gid `guest`. No home is made; `HOME` is the shared `/guest` (1777 sticky);
  `/etc/passwd` names guests and `useradd` still makes real accounts and homes. `is_guest_id`
  distinguishes them wherever code means "signed out", not `uid == GUEST`.
- **Cgroups:** a cgroup-v2-like hierarchy per namespace (`/init`, `/user`, `/system`, `/cluster`
  and subtrees), with `cpu.max`, `cpu.weight`, `memory.max`, `pids.max`, `io.max`,
  `cgroup.freeze` and `devices.allow/deny` stored and checked. Enforcement (CPU slicing,
  memory limits, freeze at syscall boundaries) is Phase 6.
- **What is not done yet:** archive jobs are not yet processes of their own (they keep their
  runner's descriptors; Phase 4); there is no pty, init program, GUI device, mount or cluster executor
  yet.

## Phase 2 findings (2026-11-01)

Uploaded wasm runs, as the roadmap's execve requires; these are built features, not roadmap.

- **Exec of an uploaded file:** `execve` of a non-`/usr` path that passes `kernel::executable`
  (regular, whole, X rule — root too needs an x bit) opens the image as a descriptor of the
  process's own (`fds.proc` = "ns pid", `fds.exec`) and answers `{fd, token_read, version}` with
  no `asset`. `version` is the immutable content id: the loader's cache key. The exec fd dies
  with the process (exit, kill, wait) or its boot.
- **The exec read token, x-only:** `token_read` is stored hashed (a capability, like process
  tokens; read tokens stay plaintext). `GET /api/file?token=` of an exec descriptor revalidates
  with the **X rule, not R** (`fds::by_token`, `kernel::namei` + `kernel::permission`), so an
  x-only 0111 file runs while a path read stays denied and a 0755→0644 chmod revokes the image
  for root too, as Linux exec reveals the image. The request must carry the owning process's
  token (`X-Process-Token`); a page or another process gets EBADF, and another browser session
  gets EPERM (the token is looked up in that request's namespace). The exec grant is never
  cached in `files.rs`'s `TOKENS`: its life ends when exit, kill or wait closes the descriptor.
- **Process-owned descriptors:** a `proc` fd answers its process's line alone (`fds::owned`), and
  lives in the line's own session (see the rules from #30 and #31): a page
  batch or another process naming it (pread, pwrite, close, FICLONE) gets EBADF. Session fds
  are unchanged. `/api/sys` batches name their process in the batch body (`pid`, `proc`); byte
  requests (`GET /api/file`, `PUT /api/pwrite`) carry `X-Process-Token`, which `api.rs` resolves
  to the process's snapshot identity, as `sys.rs` does for batches. A token that does not
  resolve, or names another browser's process, is refused with EPERM — never treated as no
  header and served as the page.
- **The loader (`web/kernel/loader.js`):** compiles once per content id (LRU 8, refreshed on a
  hit; shared promises, and a failed compile removes only its own entry), by `compileStreaming`
  when the type says wasm (`core::mime` maps `.wasm` to `application/wasm`, and an exec image
  is served as wasm whatever its name), and validates kinds and names: imports only
  functions from `wasi_snapshot_preview1`, `terminal`, `wasix_32v1`, and `env.memory` as the
  only memory; `_start`; and a memory, exported as exactly `memory` when it is not imported.
  Anything else is ENOEXEC naming the offending import, and a non-wasm file is ENOEXEC. An
  imported memory's `initial`, `maximum` and `shared` flags are read from the binary's import
  section, and each process creates one of that type (`web/wasi/process.js`); a shared memory
  without a maximum is refused. Refusals print the kernel's own errno and words when its JSON
  gives them, not one made up from the HTTP status, and glibc's words otherwise
  (`web/http.mjs` STRERROR, reused).
- **The shell's exec stage:** a stage's first word with a slash (after the system dirs' own
  meaning: `/usr/bin/NAME` and its links still run the build's) is passed as typed, with `~`
  expanded, and execs (`Shell::process`, the `(path, argv)` pair through `Shell::processes` and
  `web/wasi/exec.mjs`'s per-stage `path`); `execve` resolves it physically against the process's
  `cwd`, so the kernel decides what a relative path means. `sudo` of a coreutils applet or a
  path is the same exec stage with sudo snapshotted at exec. Bare names keep the
  builtin/terminal/coreutils tables. A failing exec says `./x: Permission denied` and the like,
  as Linux does.
- **Proven by tests:** `tests/sys.spec.js` (exec-token lifecycle, x-only, cross-session and
  page refusals, cross-namespace and zombie tokens, copied-/usr asset content, ETXTBSY, fd
  reaping) and `tests/exec.spec.js` (`./coreutils seq 3`, argv/env/
  cwd, pipeline, compile-once, pipeline statuses, 0644/0755-text/directory denials, x-only, 4755
  no elevation, failed-loader cleanup, sudo of an applet and a path, logout EPERM, Ctrl+C).


## Rules from the reviews of #30 and #31 (2026-11-03)

Settled while resolving the two reviews of phases 0–4; keep them as later phases build on them.

- **Registry policy is one table:** `kernel::registry::permit` says which route accepts each
  call and which identity it uses. `Registry` means a tokenless `X-Registry` batch, not a
  privileged kernel: any page can set that header. `Page` means a forwarded tokenless batch;
  `Process` means a batch with a process token on either route. Bookkeeping on the registry
  route acts as the account verified by the authority; process calls use their snapshot.
  `ProcInit` tracks boot ids per account and resets only that account's processes and lends.
  `Seats` filters by account (root sees all); `Gone` checks every process and lend it would
  remove before committing, with the same owner/root rule as kill. Public Web Lock names
  are liveness hints, never credentials. A mixed-account seat cannot be reaped by its guest.
  `Pids` accepts a process token too: the client keeps pools per lineage, and the server binds
  reservations to the account and, when supplied, the token. Fork cannot consume another
  account's or lineage's reservation. Unused token-bound lends expire with the last live holder.
  Fork/exit reports prove the process token. Host wait reports carry `Wait.proc`, checked
  against the zombie's stored hash, so logout does not break reaping; that token grants no
  live-process authority. Without it a registry wait needs the account/root and an init child.
  A port cannot use another host's stored token to wait. Add coverage in
  `tests/process-security.spec.js` for changes to these boundaries.
- **Cgroups have owners** (`cgroups.owner`): an account makes cgroups under `/user`
  (`registry::DELEGATED`) or its own, writes and removes its own, moves its own processes into
  its own or `/user`; root everything. Controllers are validated; device rules are capped
  (`DEVICE_RULES_MAX`).
- **Process room:** `PROC_MAX` counts live processes, pids lent and not taken (`spare`), and the
  machine's in-memory `reserved` (execs given a pid, still asking the authority). Pids are lent
  to a kernel by its id (`Pids.kernel`); each kernel holds the Web Lock `tw-kernel-<id>`, and one
  that finds another's free requests reclamation (`Gone { kernel }`), subject to account
  ownership. A new account boot drops only that account's lends.
- **Exec race:** `exec_end` replaces an image only if the row still holds the token
  `exec_begin` saw, alive (else ESRCH, and the new token is revoked); the old token is revoked
  once no fork holds it. Revocations are cleared only on the authority's answer, and a failure to
  revoke never fails the batch that ended processes (`Machine::settle`; the alarm retries).
- **Process descriptors live in their line's session** (`creds::session_of`: `proc <lineage>`,
  a job's `job <id>`), not the page's: login, logout, `su` or session expiry do not close them.
  Page batches renew every line of their namespace (`Db::renew_lines`); a line's session goes
  when its last credential is revoked (`end_line`). Descriptor numbers are per session, so a
  process and its page may each have fd 3 naming different files.
- **Descriptors keep their inode** (`fds.ino`, set by `Db::add_fd`, which also sets the idle
  expiry): `fchmod` changes that inode by any name it has (`kernel::fchmod`), never another
  inode sharing its content (FICLONE).
- **Client-kernel ownership:** each process records its host (the port, bound to the tab it
  first named); fork, reexec, exit, waitchild and kill-as-a-process need that host. A process's
  `proc_signal` is sent as the process (`kill { from }`: the batch carries its pid and token),
  after the kernel's pending reports.
- **Signals and lifetimes in the page:** an ending signal sets the process's control word
  (`KILLED | n`), heeded at its next call: it exits by the signal and closes its files itself.
  After `GRACE` (1 s) the host terminates it, releases its pipe ends, pipe locks, shared-file
  references (`Shares.release`, per-pid holders) and byte locks, and closes what it held last in
  a closer Worker (process.js `{close}`), before the exit is reported. Every kernel file a process
  opens gets a slot in its line's `Shares` (the host makes one per stage; forks inherit it) and is
  described to the host (`{described}`, `{closed}`, checked by generation). Offsets are locked
  per description from choice to update (`exclusive`). Exits carry `{exit, signal}` explicitly;
  128+n is never read back as a signal.
- **Holder tables (#36):** `Shares` and `Pipe` keep a place for every process a namespace may
  have (`PROC_MAX`; a pipe one more, for the page). A holder's place is freed once it holds
  nothing, so children one after another never fill it. A reference is only ever counted as some
  holder's (`add` and `hold` refuse, counting nothing, when no place is free; a fork checks
  `holdable` first and fails with EAGAIN), so a description's total is what its holders hold and a
  killed holder's `release` takes all of its share.
- **Fork state includes tables:** the transform exports every table and `__tw_functions` (every
  function, in order); `Engine.snapshot` records entries by function number and `Engine.child`
  sets them. Built images get the export pass without asyncify. The cache is `tw-asyncify-2`,
  and a cached image is compiled from directly.
- **/usr content in jobs:** `/internal/job/file` answers a `usr:*` content with its asset, which
  the runner streams from `ASSETS`.
- **Not taken from the reviews:** #31.8's per-pid descriptor key (a fork's child shares its
  parent's descriptions; the lifetime problem is solved by the host's release instead), and
  #31.9's second point (`SIGINT` there was the status 130 already).

## Required account semantics

These were explicitly chosen by the owner; do not silently replace them with full Linux semantics.

- guest cannot sudo. Normal sudo callers must belong to **wheel**, not a sudo/sudoers group. Root keeps full control.
- `sudo COMMAND` elevates only that request. The five-minute credential cache is used only for explicit sudo requests, with membership rechecked each time.
- `su [-] USER` switches accounts using the target password; root may switch to an enabled account without it.
- `sudo -u USER` switches the browser account and enters its home. It does not accept a trailing command.
- `exit` and `logout` revoke the session and return directly to guest at /. No nested account stack.
- Permission checks must never implicitly log guest or a normal account in as root.
- `passwd --force` skips only the 12-character minimum. It still requires a nonempty password, at most 512 bytes, and normal identity/authorization checks.
- Account changes revoke old sessions; a self-password change issues a new current session. Locking revokes sessions. Unlocking does not resurrect them.
- A signed-out browser is `guest-<uuid>:guest`, not the single uid 65534: its uid comes from 1,000,000–1,999,999, it owns what it creates in the shared `/guest`, and no home is made until `useradd -m`. Use `is_guest_id` (never `uid == GUEST`) for "signed out"; `GUEST` remains the group and the fallback identity.
- A process batch carries `pid` and `proc` (the token `Execve` answered). It runs as the credentials snapshotted at exec, with the process's umask and cgroup; it cannot login, logout, sudo or change the browser session. A page batch carries neither and keeps the old session semantics. Tokens are stored hashed, scoped to their namespace, and dead once their process is a zombie.
- `execve` requires a regular, whole file and the X permission (root too needs an x bit); setuid/setgid never elevate. Build binaries answer their asset, recognized by content so a copy or hard link of `/usr/bin/coreutils` is one too; uploaded wasm answers a descriptor of the process's own and an exec read token, revalidated with the X rule (not R) and usable only with the process's token on `GET /api/file` (`X-Process-Token`). A process token cannot `Execve` itself: a process's own execve goes through its client kernel (`reexec`), which sends `Execve { pid, proc }`.
- The client kernel runs as the browser's SharedWorker, or, where `SharedWorker` is missing, as each tab's dedicated Worker (`web/kernel/protocol.js` `kernelPort`; `client.js` serves both, its port `self` when dedicated). A tab holds the Web Lock `tw-tab-<tab>` from before its first request, and every request carries `tab`; `execve` records it as the process's `seat` (`processes.seat`, `Proc.seat`). The kernel reaps a process whose seat's lock is free (`Gone`, SIGKILL then init's reap): at once where a SharedWorker waits on a tab's lock (`watch`), and at boot and on EAGAIN by `Seats` and `locks.query()` (`reapGone`). Only a SharedWorker without Web Locks reaps by boot id (`ProcInit { boot }`); never a tab's own kernel, which would reap other tabs' processes. `tests/kernel.spec.js` covers a closed tab and the no-SharedWorker fallback.
- `/proc` lists the caller's namespace (`procfs` takes `ns`, `Db::namespace(key, guest)`): PIDs are per namespace. A process names only its own descriptors and a page only the page's (`fds::owned`, and `by_token` for read tokens): a process never reaches a page's descriptor, those opened as root under sudo included.

## UX requirements and fragile areas

- Main text is 20px.
- The desktop (owner's request, 2026-10-30: "a windows compositor … should not draw directly on canvas, it calls browser api … These should be wasm"; step 1 of the plan toward init, a greeter, a kernel of processes and outside GUI apps).
  - `crates/frontend/src/desktop.rs` lays out DOM windows (`.window`, `data-window`, one of `APPS`) absolutely within `.desktop-area`, by inline style (left, top, width, height, z-index 20 + rank), from `Desktop.windows`. Frames are kept per browser in localStorage `os-desktop`.
  - The viewer's and editor's `<dialog>`s are adopted: moved into the area, given handles and buttons, and followed by their `open` attribute. They open with `show()`, never `showModal()`; a closed dialog is not marked `window-hidden`, so it can take the focus the moment it opens.
  - Only the sign-in dialog is modal. "A dialog is in the way" is `dialog[open]:modal`; "another window has the keyboard" is `.window:not(#window-terminal)` (app.js `restoreTerminalFocus`, the typing redirect). The Files window takes focus (`tabindex=-1`), so a click there keeps the keyboard there.
  - Up to 650 px wide (`COMPACT`, as the CSS), one window shows at a time, filling the area; there is no maximize button.
- Restrained colors, line icons, highlighted prompts, and ls-style listings are intentional. Terminal scrollbars are hidden, but scrolling must work.
- Completion takes from each command's clap definition which operands and option values are paths (`value_hint`: `DirPath` for directories, `AnyPath` otherwise; core test `path_operands_say_so_for_completion` fails for a path operand without one). Completion is fish-like: the first Tab only lists the fuzzy candidates (owner's request, 2026-10-28: so that more may be typed to narrow them), unless there is one, which completes at once (`CompletionSession::selected` is `None` until one is picked); Tab and Shift+Tab then cycle the original candidates, empty input browses files, quoting and Unicode are preserved, and stale asynchronous results are discarded.
- Every command has -h / --help, from its clap definition, as is its man page. Help must run before authentication or side effects (the shell answers it before dispatch). Respect -- when interpreting help flags.
- Wildcards (owner's request, 2026-10-26) expand as bash expands them: in the page, per stage as it starts (`Shell::expand`), listing with the caller's permissions; matching and quoting rules are in core (`glob.rs`, `shell::words`). Items xargs reads and fd -x placeholders are never expanded, as in a shell.
- Live changes (owner's request, 2026-10-26): every page keeps a WebSocket to the authority (`/api/events`, origin-checked in the Worker, hibernatable, pings auto-answered). `Db` notes the directories a committed transaction changed (`set_node`, `delete_node`, chunk commits); the authority sends each socket only those its session's account may list (READ|EXEC), after every request and after the alarm. Node writes must keep going through `set_node`/`delete_node` so that they are heard. Pages send one thing on it (owner's request, 2026-10-28): `{"present": {"path", "at": [column, row]}}`, the slide or presented PDF page they show (`terminal.present`, from viewer.rs); `OsAuthority::relay` passes it to the sockets of the same account in other sessions (other browsers; never for guest), and the windows of one browser hear it from each other (`BroadcastChannel('os-present')`); app.js turns both into `os:present`, which the deck or PDF showing that path follows without saying it again.
- Uploads: the file chooser opens synchronously in the gesture (`Shell::run` calls `terminal.chooseFiles()` before anything is awaited; phones refuse it later); Ctrl+C or closing the tab settles a chooser still open with no files (`cancelChoosing`), as a browser may close one without a cancel event. Dropped files go to the active tab, or, dropped on the Files window, into the Files' directory (app.js `files-dropped`). A tab's upload's progress is a live line in its transcript; the Files' is their own (`files.rs`, `Upload progress`, with Cancel); there is no page-level notice. Progress, there and in listings (`Entry.uploaded`, `Db::received`), is the bytes of the committed chunks, wherever they are; `Db::readable`, the prefix readers get, is for reading. One descriptor writes a file at a time (owner's request, 2026-10-27): the uploading page keeps it (`lease`, upload.mjs) and closes it when it stops or goes; another page goes on with the same file only once it is closed or `fds::LEASE` passed, and the old descriptor then writes no more. The result is kept in Cache Storage (`tw-asyncify-1`) by content. Only the features browsers run are enabled: binaryen's compact imports would change the binary.
  - **The engine (`web/wasi/fork.js`):** the unwind buffer is memory grown for it once (4 pages), so no layout is guessed. A fork unwinds out of `_start`; the run loop posts `{fork}` with a copy of memory and mutable globals; the page (`exec.mjs` `host`) asks the client kernel for the pid, holds the child's pipe ends for it, and starts it in a Worker that rewinds with 0; the parent rewinds with the pid. setjmp saves the unwound stack and the shadow stack (keyed by the jmp_buf's address); longjmp restores both and rewinds.
  - **Waiting calls:** `proc_join`, `proc_exec`, `proc_parent` and `proc_signal` post `{host}` and wait on the process's `channel` (shared memory, 64 KiB, JSON), heeding a stop every 200 ms. `join` asks the client kernel's `waitchild` (wait4 over its table: ECHILD, EAGAIN, or the zombie reaped) and waits for the next exit of a hosted process. `exec` asks `reexec`, loads the image, posts `{image}`, and the process throws out of its image (`Replaced`) and starts the new one in the same Worker, closing close-on-exec descriptors; a format refused after the kernel replaced the image ends the process (126).
  - **Shared open files (`web/wasi/shared.js`):** a fork line shares a table (`Shares`) of each open file's descriptor count and offset; a description is counted per descriptor in every process, and only the last close closes it at the kernel or commits it. Files being written keep their bytes in `Bytes` (a growable SharedArrayBuffer and a lock). Pipes count holders by pid (`pipe.js` `hold`, `drop`, `release`); an end is gone when its holders are, and only the end a holder let go of is settled; the page holds a stage's or child's ends before it starts, the terminal's writing end itself (`PAGE`), and releases a process it ends (`exec.mjs` `release`). Stdin given as bytes is copied, not shared.
  - **Jobs and reaping:** forks are in their stage's job (`forks`): Ctrl+C, Ctrl+Z and `fg` reach them; the pipeline's status is still its stages'. A fork's exit is only an exit (`reap(..., forked)`); its parent waits, and the page reaps it only once it is init's (the client kernel's `exit` answers the parent). Background children outlive the job, as Linux's do.
  - **Fixture limits:** the approved `dash` (2023) keeps its own working directory, starting at `/`, until `cd`; and its `printf` into a file or pipe loses what follows the first line (its stdio is never flushed). Neither is the runtime's.

- The transcript renders ANSI (owner, 2026-10-29: "ANSI color support is necessary, now"): core `ansi.rs` parses SGR (16, 256, 24-bit colours; bold, dim, italic, underline, inverse, strike) and OSC 8 links into runs, dropping other CSI/OSC sequences; frontend `render_line` draws them, the 16 colours as `--ansi-N` in style.css. The WASI engine tells a program its stdout is a terminal unless piped.
- The tree is Arch's (owner: "mine is /sbin -> /usr/bin … change to the same"): usr.rs `TREE` (bin, sbin, lib, lib64 links; /usr's directories; /sys empty and 555), and sys.rs `ensure` (/boot, /mnt, /opt, /run, /srv, /var 755; /tmp 1777); /root is made 750. A typed /bin, /sbin, /usr/sbin or /usr/bin path runs its name (`bin::named`).
