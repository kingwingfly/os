## Architecture contract

The [README architecture](README.md#client-os-and-remote-services) and #44 define the target; the [architecture contract](docs/architecture/contract.md) (Contract v2, amended in L0c #76) records the decisions the steps follow. Keep current limitations explicit; do not describe planned features as implemented.

- Each OS instance owns its client kernel, local process/signals/descriptor/VFS/mount namespace semantics, local `/proc`, `/run`, `/tmp`, IPC, local devices, local resource accounting, local `os-cowfs` root volume, PID 1, and sessions. Remote service adapters supply authenticated filesystem, `ServiceAuth v2` credential, remote device/execution, relay, volume, registry, and dispatch contracts. Cloudflare is the first provider; local syscalls and remote protocols are separate interfaces.
- Instance, execution host, local OS account, explicit cloud service credential, login session, seat, and app window are distinct identities. A fresh boot creates an instance with a locally generated random boot ID and zero outbound network requests; additional pages attach only explicitly where supported. Sharing an account, cookie, or remote volume does not merge kernels or namespaces. A new instance boots from a verified offline Release v2 generation and local `os-cowfs` root volume (or an O(1) persistent fork when another tab holds `os-vol:<uuid>`), not another user's live memory or secrets.
- **100% local OS accounts decoupled from explicit cloud service credentials (Contract v2 §2.4).** Each instance's root volume owns `/etc/passwd`, `/etc/group`, and `/etc/shadow` (`#57`); local `uid 0` genuinely owns its instance and local root volume and **never** synthesizes remote root. Remote services authorize solely on explicit userspace cloud service credentials (`Boundary::ServiceAuth` v2) acquired via Cloud/Cluster Sign-In or CLI tools. `FsType::Cloud` is retained feature-frozen as an optional remote filesystem (`/mnt/cloud`), not deleted in `#65`; multi-client shared live machines use Phase 9 remote seat/PTY attach onto a hosted `os-native`/Container instance (`#82`).
- Boot: Stage 0 host loader verifies the locally pinned signed Release v2 boot set (`#78`) → Stage 1 kernel creates the initial `tmpfs` root and executes early `/init` as PID 1 offline with local devices only → Stage 2 early `/init` mounts the local `os-cowfs` root volume (`#77`, provisioning defaults on first boot or O(1) persistent fork if another tab holds `os-vol:<uuid>`) plus verified `/sysroot/usr` and `/sysroot/tmp`, detaches Stage-1 `/usr`, performs `switch_root`, and `execve`s main `/usr/bin/init` retaining PID 1 (`#56`) → system services and optional post-switch remote units (`cloud.mount`, `devattach@*`, `kubelet.service`) (`#57`). Systemd is a lifecycle reference; upstream systemd/unit-file compatibility is not claimed.
- `xtask` assembles/verifies Release v2 boot artifacts (`initramfs`, `root-template`, `base`, `sysext`, `confext`, `workload`). Wrangler deploys them. Cargo features select compiled capabilities; service/mount configuration controls startup. `/boot` contains release and early-userspace references, never user data or private signing keys.
- Separate source/device, filesystem instance, inode, open description, mount attachment, namespace and export. L1 supplies stable identity, persistent ownership/modes/ACLs/xattrs, actual flush semantics and declared cross-client consistency. L2 uses one mount model across all 11 canonical `FsType`s (`cloud`, `cowfs`, `opfs`, `hostfs`, `helperfs`, `sharefs`, `image`, `tmpfs`, `proc`, `devtmpfs`, `devpts`), including busy unmount, lazy detach, revocation and provider loss as distinct operations.
- L2 implements actual `chroot`: syscall/runtime ABI plus ordinary command, per-process root/cwd/mount context, physical path and executable lookup (including `#!` shebangs and zero outside-root fallback), privilege/errno, fork inheritance and exec preservation. The syscall does not chdir, close fds or create namespaces; the utility changes to its new root then execs. Outside cwd/retained fds keep their documented semantics within original grants. Chroot alone is not a sandbox or the boot root-switch operation.
- Host folders and browser storage expose existing filesystem trees without directory copying. Multiple attachments need stable shared identity/metadata. `os-cowfs` (`crates/cowtree`, `crates/cowfs`) provides MIT pure-Rust Merkle CoW storage behind pluggable `HeadStore`/`PackStore` traits with managed `/dev/vdN` devices (`BLK_INFO`/`BLK_LEASE`/`COWFS_IOC_*`); `mkfs.cowfs` refuses directory, host-folder, browser-storage, and export tree sources with `ENOTBLK`, and mounting a tree never formats it. Opening a `cowfs` store with an incompatible `COWFS_FORMAT_VERSION` fails with `EPROTONOSUPPORT` and never silently wipes user data.
- Filesystem exports are userspace VFS services. Account ACLs or export-scoped passwords define access; receivers explicitly mount. Local IPC, P2P and relay must enforce identical authority, lifetime, cancellation and uncertain-write rules. Shared cloud paths generally need ACLs instead of re-export. A live export needs its host; a relay does not provide storage replication.
- Userspace compositor owns display/input and surface isolation. Desktop-shell panel/background/launcher roles are explicit. Files, Terminal, Mounts, Editor and Preview become ordinary supervised OS processes in L6; Terminal launches a separate shell through a PTY. Portable controllers/services remain outside rendering; browser/native display, input, picker, clipboard, IME and accessibility belong to host adapters.
- Preserve archive/media acceleration through typed devices: execute near granted cloud data, stream bulk bytes through authorized storage gateways, and return status/results. Logical boot-distribution and resource/acceleration roles may share a deployment. General CPU/GPU placement is later explicit task work, with capability/privacy/consent/quota/cost constraints; no arbitrary program is automatically distributed by name.
- Provider adapters translate versioned OS contracts (`HostAdapter v2`, `ServiceAuth v2`, `RemoteFilesystem v2`, `Release v2`, `LocalHelper v1`, `DeviceTask v1`, `Gui v1`, plus reserved `Volume v1`, `Registry v1`, `ClusterState v1`, `Network v1`) into backend APIs and enforce the resource authority. They must advertise/reject unsupported filesystem/runtime guarantees honestly. Reusing path/permission code on a server is valid. Client root, pathnames, digests, instance IDs and claimed PIDs never grant remote administrator authority.
- L0 defines a portable dispatch contract; Phase 9.2-Q implements Cloudflare Queues after the task foundation (`#83` `ClusterState`). Durable task state/outbox, idempotency, attempt leases/fencing, recoverable handoff, cancellation/revocation, bounded retries/DLQ and fairness remain task-service responsibilities. Queue messages contain scoped references, not bulk bytes or provider account secrets. Keep interactive VFS, PTY/signals, GUI and media on direct/streaming paths. No Queues infrastructure is configured today.
- Virtual NIC/socket stack (`#86` `netd`, `#87` `/dev/net/tun`), additional cloud/OpenDAL adapters, native Wasmtime execution (`#82` `os-native` + standalone OCI container image), and GPU/shared-storage backends retain separate gates. Linux ELF pod delegation is explicitly deferred/out of scope (Wasm/WASIX hosts reject ELF with `ENOEXEC`). Browser transports do not imply raw TCP/UDP. The headless native CPU agent is a Phase 9 deliverable; a desktop wrapper alone does not provide an executor.

## Security and data invariants

- The service authenticates every resource operation, including HEAD, Range, conditional responses and executable reads. Public routing headers, Web Lock names, numeric IDs and client-reported hashes are not credentials. `ServiceAuth v2` remote service tokens authorize only their recorded `(instance_id, host_proof)` fence, lineage, scope, and rights; account changes cannot rewrite running process identities, and local `uid 0` never synthesizes remote root.
- Current process credentials preserve umask/cgroup/generation and descriptor ownership through fork/exec. Local `fork` executes inside `LocalProcessTable` with zero server RPC, inheriting attenuated remote credentials when present; local privilege drops (`set_cred`) clear ambient remote credentials and immediately revoke dropped tokens over `ServiceAuth v2`. Ordinary exec inherits cloud-open grants before retiring its token, preserving forked holders; explicit revocation or expiry releases the final grant and its locks. Job credentials must use their scoped path API; v2 rejects them until it supports equivalent grant restrictions. Shared open descriptions retain offsets/flags and counted holders; killed processes release holders before parent wait completion. Exec races must not revive revoked tokens; revocation retries remain durable (`Machine` DO `pending_revocations` alarm flush).
- Root still needs an executable bit. Uploaded setuid/setgid metadata does not elevate. Executable-only reads are scoped to execution; they do not grant general read access. Local kernel privilege cannot bypass remote service checks or the host picker/helper ceiling.
- VFS checks cover ancestor traversal, correct owner/group/other selection, named/default ACLs, sticky directories and protected links. Creation uses creator credentials, requested mode, the current per-call umask/default ACL and setgid inheritance. The cloud creation calls carry the current mask separately from mode, and skip truncate-on-open for a newly created empty file. Both namespace protocols reserve absent account homes and route interactive-device unlink through its driver. Keep permission behavior in shared filesystem rules and service authorization, not DOM handlers.
- Filesystem metadata decisions and commits use synchronous authority transactions; never await inside one. Async work occurs outside, followed by revalidation. ## Account behavior

These are current `OsAuthority`-backed browser account/session behaviors until `#57` (`L3d`) moves OS accounts 100% local (`/etc/{passwd,group,shadow}`) and introduces the Cloud/Cluster Sign-In panel (decoupling local OS users from explicit `ServiceAuth v2` cloud credentials). A #44 change to them needs a deliberate decision and denial tests rather than an accidental UI/API change; no migration of existing accounts or sessions is needed.

- Individual signed-out identities are `guest-<id>` in group guest, uid 1,000,000–1,999,999. Use `is_guest_id`; reserved uid/gid 65534 is the fallback/group. Shared `/guest` is sticky; `useradd -m` creates a private home. Both namespace protocols reject renaming registered homes or their containing directories; use `usermod -d HOME -m NAME` to move an existing home with its account record.
- Guest cannot sudo; ordinary sudo callers need wheel membership, rechecked for explicit requests. `sudo COMMAND` elevates that command only; the credential cache lasts five minutes. `su` uses the target password except for authorized root switching. Current `sudo -u USER` switches the browser account without accepting a trailing command.
- Logout/exit revokes the browser session and returns to guest without a nested account stack. Existing process snapshots remain separate; explicit login shutdown is a different lifecycle operation. Locking/account changes revoke old sessions; unlocking never revives them.
- `passwd --force` skips the minimum length only; the password must remain nonempty and within 512 bytes. Permission failures never implicitly sign in as root.
