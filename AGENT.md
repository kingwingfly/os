## Architecture contract

The [README architecture](README.md#client-os-and-remote-services) and [architecture contract](docs/architecture/contract.md) (Contract v2) describe the implemented architecture. Keep current limitations explicit; do not describe planned Phase 9–10 features as implemented.

- Each OS instance owns its client kernel, local process/signals/descriptor/VFS/mount namespace semantics, local `/proc`, `/run`, `/tmp`, `AF_UNIX` IPC, local devices, local resource accounting, local `os-cowfs` root volume, PID 1, service graph, and sessions. Remote service adapters supply authenticated optional `CloudFs` (`/mnt/cloud`), `ServiceAuth v2` credentials, remote device/execution, relay, volume, registry, and cluster-state contracts. Cloudflare is the first backend; local syscalls and remote protocols are separate interfaces.
- Instance, execution host, local OS account, explicit cloud service credential, login session, seat, and app window are distinct identities. A fresh boot creates an instance with a locally generated random boot ID and zero outbound network requests; additional pages attach only explicitly where supported. Sharing an account, cookie, or remote volume does not merge kernels or namespaces. A new instance boots from a verified offline Release v2 generation and local `os-cowfs` root volume (or an O(1) persistent fork when another tab holds `os-vol:<uuid>`), not another user's live memory or secrets.
- **100% local OS accounts decoupled from explicit cloud service credentials (Contract v2 §2.4).** Each instance's `os-cowfs` root volume owns `/etc/passwd`, `/etc/group`, and `/etc/shadow` (`#57`); fresh boot auto-logs in as local `user` (uid 1000, in `wheel`). Local `uid 0` genuinely owns its instance and local root volume and **never** synthesizes remote root. Remote services authorize solely on explicit userspace cloud service credentials (`ServiceAuth v2`) acquired via Cloud/Cluster Sign-In or CLI tools. `FsType::Cloud` is retained feature-frozen as an optional remote filesystem (`/mnt/cloud`, `#75`); multi-client shared live machines use Phase 9 remote seat/PTY attach onto a hosted `os-native`/Container instance (`#82`).
- Boot: Stage 0 host loader verifies the locally pinned signed Release v2 boot set (`#78`) → Stage 1 kernel creates the initial `tmpfs` root and executes early `/init` as PID 1 offline with local devices only → Stage 2 early `/init` mounts the local `os-cowfs` root volume (`#77`, provisioning defaults on first boot or O(1) persistent fork if another tab holds `os-vol:<uuid>`) plus verified `/sysroot/usr` and `/sysroot/tmp`, detaches Stage-1 `/usr`, performs `switch_root`, and `execve`s main `/usr/bin/init` retaining PID 1 (`#56`) → system service manager activates `graphical.target` or `multi-user.target` and optional post-switch remote units (`cloud.mount`, `devattach@*`, `kubelet.service`) (`#57`). Systemd is a lifecycle reference; upstream systemd unit compatibility is not claimed.
- `xtask` assembles/verifies Release v2 boot artifacts (`initramfs`, `root-template`, `base`, `sysext`, `confext`, `workload`). Wrangler deploys them. Cargo features select compiled capabilities; service/mount configuration controls startup. `/boot` contains release and early-userspace references, never user data or private signing keys.
- Source/device, filesystem instance, inode, open description, mount attachment, namespace, and export are separate concepts across all 11 canonical `FsType`s (`cloud`, `cowfs`, `opfs`, `hostfs`, `helperfs`, `sharefs`, `image`, `tmpfs`, `proc`, `devtmpfs`, `devpts`), including busy unmount, lazy detach, revocation, and provider loss as distinct operations, plus real `chroot` with `#!` shebangs and zero outside-root fallback.
- Host folders and browser storage expose existing filesystem trees without directory copying. `os-cowfs` (`crates/cowtree`, `crates/cowfs`) provides MIT pure-Rust Merkle CoW storage behind pluggable `HeadStore`/`PackStore` traits with managed `/dev/vdN` devices (`BLK_INFO`/`BLK_LEASE`/`COWFS_IOC_*`); `mkfs.cowfs` refuses directory, host-folder, browser-storage, and export tree sources with `ENOTBLK`, and mounting a tree never formats it. Opening a `cowfs` store with an incompatible `COWFS_FORMAT_VERSION` fails with `EPROTONOSUPPORT` and never silently wipes user data.
- Userspace `mountd` (`/run/user/<uid>/mount.sock`) and `exportd` (`/run/user/<uid>/export.sock`) unify CLI and GUI mounts and filesystem exports over `AF_UNIX` + `SO_PEERCRED` + `SCM_RIGHTS`. Account ACLs or export-scoped passwords define access; receivers explicitly mount. Local IPC, P2P, and relay enforce identical authority, lifetime, cancellation, and uncertain-write rules.
- Supervised userspace `compositor` (`/dev/display`, `/dev/input`, `/run/gui/seat0.sock`) and `desktop-shell` (`Panel`/`Background`/`Launcher` via kernel `PEER_ROLES`) own display, input, focus, snap zones, and layout persistence (`~/.config/os/desktop-layout.json`). All five built-in desktop apps — **Terminal** (`/usr/bin/terminal` + `/usr/bin/osh` on UNIX 98 PTYs), **Files** (`/usr/bin/files`), **Mounts** (`/usr/bin/mounts`), **Editor** (`/usr/bin/editor`), and **Preview** (`/usr/bin/preview`) — run as ordinary unprivileged GUI `SurfaceKind::Document` processes. Portable controllers/services contain zero DOM types; browser/native display, input, picker, clipboard, IME, media, and accessibility belong to thin host adapters (`web/gui/`, `crates/frontend/`).
- Provider adapters translate versioned OS contracts (`HostAdapter v2`, `ServiceAuth v2`, `RemoteFilesystem v2`, `Release v2`, `LocalHelper v1`, `DeviceTask v1`, `Gui v1`, `Volume v1`, `Registry v1`, `ClusterState v1`, `Network v1`) into backend APIs and enforce resource authority. Client root, pathnames, digests, instance IDs, and claimed PIDs never grant remote administrator authority.
- `/dev/net/tun` L3 tenant overlay (`#87`), Cloudflare Queues dispatch (`Phase 9.2-Q`), additional cloud/OpenDAL adapters, and GPU backends retain separate gates. Linux ELF pod delegation is explicitly out of scope (Wasm/WASIX hosts reject ELF with `ENOEXEC`).

## Security and data invariants

- Remote services authenticate every resource operation (`HEAD`, `Range`, conditional responses, executable reads). Public routing headers, Web Lock names, numeric IDs, and client-reported hashes are not credentials. `ServiceAuth v2` remote service tokens authorize only their recorded `(instance_id, host_proof)` fence, lineage, scope, and rights; local account switches cannot rewrite running process identities, and local `uid 0` never synthesizes remote root.
- Current process credentials preserve umask/cgroup/generation and descriptor ownership through fork/exec. Local `fork` executes inside `LocalProcessTable` with zero server RPC, inheriting attenuated remote credentials when present; local privilege drops (`set_cred`) clear ambient remote credentials and immediately revoke dropped tokens over `ServiceAuth v2`. Killed processes release descriptor holders before parent wait completion.
- Root still needs an executable bit. Uploaded setuid/setgid metadata never elevates. Only `wasi_snapshot_preview1`, `os`, and `wasix_32v1` WASM import namespaces are accepted (`"terminal"` fails with `ENOEXEC` / exit 126).
- VFS checks cover ancestor traversal, owner/group/other selection, named/default ACLs, sticky directories, and protected links. Keep permission behavior in shared Rust `os-vfs` rules and service authorization, never in DOM handlers.
- `.dev.vars`, `.local-password`, and `.wrangler` contain private local state. Never print or commit secrets. `ADMIN_PASSWORD` initializes cloud root once; `SESSION_SECRET` is the password pepper and must be restored with data.
- Current format/schema versions: `OsAuthority` `SCHEMA_VERSION = "10"` (`os_image::SCHEMA = 10`), `Machine` DO `MACHINE_SCHEMA_VERSION = 4`, `os-cowfs` `COWFS_FORMAT_VERSION = 1` (magic `"OSCOWFS1"`), browser metadata `STORE_FORMAT_VERSION = 3`, helper metadata `STATE_FORMAT_VERSION = 3`. Derived metadata caches reset without touching user files on older versions; an `os-cowfs` user volume **never** silently resets on version mismatch (`EPROTONOSUPPORT` into recovery). Never attach an empty unrelated authority to an initialized bucket.

## Local accounts and Cloud Sign-In

- **Local OS accounts** live in `/etc/passwd`, `/etc/group`, and `/etc/shadow` inside each instance's local `os-cowfs` root volume (100% offline, zero network RPCs). Default fresh boot signs in as `user` (uid 1000, in `wheel`). `su`, `sudo`, `login`, `passwd`, `useradd`, `usermod`, `userdel`, `groupadd`, `groupmod`, and `groupdel` operate locally via `/usr/bin/*` and `/login.html`. Running processes retain their captured credentials across local account switches; local `root` owns only the local instance.
- **Explicit Cloud / Cluster Sign-In** (`/api/cloud-auth/{login,logout,status,register}`, top-bar panel) authenticates a remote Cloud account and mints scoped `ServiceAuth v2` credentials (`cloud_fs`, `devices`, `containers`, `relay`) without modifying local `/etc/passwd` or local UIDs. Signing out of Cloud unmounts `/mnt/cloud` and revokes remote credentials while leaving local processes unaffected.
